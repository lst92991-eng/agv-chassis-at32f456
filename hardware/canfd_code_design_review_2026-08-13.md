## 3. P0：整车准入阻断项

### P0-01 STOP/ESTOP 不是普通命令队列屏障

- **状态**：待修复
- **代码证据**：
  - `src/app_freertos.c:96-109`：GOTO、CLEAR_FAULT 等进入普通 FreeRTOS 队列，STOP/ESTOP 等进入独立优先槽。
  - `src/app_freertos.c:161-170`：控制任务先处理优先槽，随后仍继续排空普通队列。
  - `src/chassis_motion_controller.c:681-746`：无故障时 GOTO 可启动任务。
  - `src/chassis_motion_controller.c:749-769`：STOP/ESTOP 停车或锁存故障。
  - `src/canfd_protocol.c:359-368`：协议在命令入队时提前切换运动会话状态。
- **可达场景**：
  1. 在一个 10 ms 控制周期前依次收到 `GOTO -> STOP`。
  2. STOP 从优先槽先执行并返回 ACK。
  3. 普通队列中的旧 GOTO 随后执行，电机重新启动。
  4. 协议层已因 STOP 清除 `motion_session_active`，重新启动的旧 GOTO 还可能失去 300 ms 心跳保护。
- **风险**：主控认为 STOP 已生效，但电机随后执行旧运动命令。
- **整改要求**：
  - STOP、ESTOP、COMM_TIMEOUT、CAN 链路故障必须形成命令屏障。
  - 安全事件发生后，清空或代际作废此前所有普通命令。
  - 本控制周期处理过安全命令后，不得继续消费普通命令。
  - 建议为命令增加 `safety_epoch`，执行前核对入队代际。
- **验收测试**：小于 10 ms 间隔注入 `GOTO -> STOP`、`GOTO -> ESTOP`，STOP/ESTOP 后 PWM 不得再次恢复，旧命令必须收到 CANCELED 或失效结果。

### P0-02 旧 CLEAR_FAULT 可以覆盖更新的安全故障

- **状态**：待修复
- **代码证据**：
  - `src/app_freertos.c:161-170`：ESTOP 优先执行后仍会处理旧普通命令。
  - `src/chassis_motion_controller.c:763-769`：ESTOP 锁存 `CHASSIS_FAULT_ESTOP`。
  - `src/chassis_motion_controller.c:813-835`：CLEAR_FAULT 没有故障代际检查，直接清除全部故障位。
- **可达场景**：同一控制周期前依次收到 `CLEAR_FAULT -> GOTO -> ESTOP`，实际可能执行为 `ESTOP -> CLEAR_FAULT -> GOTO`。
- **风险**：刚产生的 ESTOP、COMM_TIMEOUT 或 CAN 链路故障被更早入队的清故障请求立即覆盖，随后旧运动重新启动。
- **整改要求**：
  - CLEAR_FAULT 必须携带或绑定故障代际，只能清除请求之后确认可恢复的故障。
  - 新安全事件出现后，所有更早的 CLEAR_FAULT 自动失效。
  - ESTOP 建议增加明确的释放/复位状态，并在清故障后要求新的 ARM/ENABLE。
- **验收测试**：注入 `CLEAR_FAULT -> GOTO -> ESTOP`，ESTOP 必须保持锁存，普通队列全部失效，电机持续制动。

### P0-03 CPU 异常和任务失活缺少独立电机安全门

- **状态**：待设计、待修复
- **代码证据**：
  - `src/at32f45x_int.c:46-99`：NMI 为空，HardFault、MemManage、BusFault、UsageFault 仅死循环。
  - `src/app_freertos.c:282-300`：栈溢出和 RTOS assert 会制动，但不能覆盖所有 CPU 异常和任务卡死。
  - 当前正式控制链未找到独立 WDT/WWDT 初始化与健康喂狗逻辑。
- **风险**：电机运行中发生 CPU 异常或控制任务卡死时，TMR8 PWM 可能保持故障前输出。
- **整改要求**：
  - 异常入口首先进入不依赖 RTOS 的底层安全停机路径，关闭 PWM 输出或触发硬件制动。
  - 增加独立看门狗，由控制任务健康状态和关键任务心跳共同决定是否喂狗。
  - 评估使用 TMR8 Break、驱动使能或硬件急停链切断输出。
- **验收测试**：PWM 运行时注入 HardFault、关闭控制任务调度、模拟死循环，验证规定时间内输出进入安全态。

### P0-04 过流、欠压和物理急停尚未进入正式安全链

- **状态**：待硬件参数确认、待实现
- **代码证据**：
  - `src/motor_current.c` 仅在 ADC/电流测试代码中使用，未接入正式底盘故障状态机。
  - `hardware/motor_board_netlist_review.md:15-20`：AT8236 理论斩波限流约 5 A，高于电机约 0.7 A 堵转电流，不能替代 MCU 保护。
  - 当前 ESTOP 是 CAN 命令，未看到独立物理急停输入或硬件切断链。
- **风险**：堵转、短路趋势、母线欠压或 CPU/CAN 失效时，仅靠现有软件状态机不能形成完整保护。
- **整改要求**：带载测定左右电机正常峰值、堵转趋势和电池范围后，增加过流、欠压、恢复迟滞、持续时间和独立故障位；明确物理急停方案。
- **验收测试**：堵转、过载、欠压、恢复、电源抖动和物理急停测试，验证本地停车、故障锁存及 CAN 事件上报。

## 4. P1：高优先级协议与实现问题

### P1-01 CAN 运动会话生命周期与真实任务脱节

- **状态**：待修复
- **代码证据**：
  - `src/canfd_protocol.c:351-368`：GOTO 只要入队成功就置 `canfd_motion_session_active=1`。
  - `src/canfd_protocol.c:977-985`：COMPLETED、CANCELED、FAULT 事件只发送 ACK，不结束运动 lease。
  - `src/chassis_motion_controller.c:390-419`：任务终态发生在异步控制任务中。
  - `tools/canfd_agv_test.py:446-448`：命令行工具收到 COMPLETED 后直接返回成功，不补 STOP。
- **风险**：任务完成、被拒绝或被其他来源取消后，主机停止心跳，固件约 300 ms 后仍可能误锁存 `COMM_TIMEOUT 0x0010`。
- **整改要求**：由底盘控制器在 ACCEPTED、REJECTED、COMPLETED、CANCELED、FAULT 时显式通知协议层更新 lease；协议层不得以“成功入队”等同于“运动中”。
- **验收测试**：完成、拒绝、串口取消和故障后停发心跳 1 s，不得新增伪通信故障。

### P1-02 心跳没有验证新鲜度，GUI 周期发送固定心跳

- **状态**：待固件与上位机同时修复
- **代码证据**：
  - `src/canfd_protocol.c:434-469`：心跳只验证非零序号、session 和 CRC，没有检查序号或主机 uptime 是否递增。
  - `src/plugins/control/raw_control/RawControlPlugin.cpp:227-237`：周期发送重复使用同一十六进制帧。
  - `RawControlPlugin.cpp:367`：默认心跳固定 `sequence=1`、`uptime=0`。
- **风险**：重复、乱序或链路恢复后成批到达的旧心跳仍能续租，无法证明当前主控应用仍在运行。
- **整改要求**：每帧递增 heartbeat sequence 和 uptime；固件在当前 session 内拒绝重复/旧心跳，并定义回绕规则。
- **验收测试**：持续重放完全相同的有效心跳，运动 lease 应在 300 ms 后超时；正常递增和 `65535 -> 1` 回绕不得误报。

### P1-03 Qt 上位机同步 WinUSB 写无背压和安全抢占

- **状态**：待修复
- **代码证据**：
  - `RawControlPlugin.cpp:218-237`：GUI QTimer 每 100 ms 无条件产生心跳。
  - `src/core/DebugCore.cpp:144-187`：每条命令通过 Qt 队列排入协议线程，队列没有容量和合并策略。
  - `CandleLightCanFdPlugin.cpp:291-320`：WinUSB 写同步执行，默认超时最长 500 ms。
- **风险**：一次写超时后，心跳生产速度可约为消费速度的 5 倍，旧心跳、运动命令和后来的 STOP/ESTOP 持续积压；拔 USB 或断开后 Periodic 仍可继续制造错误。
- **整改要求**：
  - 建立有界单写队列；周期心跳只保留最新一帧。
  - STOP/ESTOP 必须抢占并丢弃普通待发命令。
  - 写超时立即停止 Periodic、清理普通队列并进入断线状态。
  - 重连必须建立新连接代次和新 session，旧命令不得穿越重连。
- **验收测试**：模拟 500 ms 写超时、拔插 USB 和读线程退出，确认队列有界、无错误风暴，STOP/ESTOP 不被旧心跳阻塞。

### P1-04 CAN 发送故障状态与 CLEAR_FAULT 条件不闭环

- **状态**：待修复
- **代码证据**：
  - `src/canfd_protocol.c:783-804`：发送超时只首次提交 CAN 链路故障，成功发送后才清 `canfd_tx_link_fault_reported`。
  - `src/chassis_motion_controller.c:813-835`：CLEAR_FAULT 不检查 Bus-Off、近期 TX 成功或双向链路健康。
- **风险**：单向 TX 故障时，板端可能继续收到心跳和 CLEAR_FAULT，清除故障并接受运动，却无法上报 ACK 或安全事件；若故障上报锁保持，后续发送失败可能不再重新锁存。
- **整改要求**：将“当前链路健康”“故障已经上报”“恢复尝试状态”分开管理；至少一次成功 TX 且错误状态解除后，才允许清除链路故障。
- **验收测试**：分别模拟只收不发、立即写失败、发送超时、Bus-Off 和恢复中再次失败。

### P1-05 CAN TX 立即失败没有进入超时恢复路径

- **状态**：待修复
- **代码证据**：`src/canfd_protocol.c:774-805` 只监控已进入 `canfd_tx_inflight` 的发送；`canfd_txbuf_write/transmit` 在 `825-834` 立即返回失败时只会下次轮询重试。
- **风险**：硬件 API 持续立即失败时，固件不会触发 50 ms 超时、链路恢复或本地停车。
- **整改要求**：为提交阶段增加连续失败计数和时间上限，进入与发送卡住一致的链路故障恢复路径。
- **验收测试**：桩替换两个底层 API，使其持续返回失败，验证在限定时间内制动、锁存和重置 CAN3。

### P1-06 紧急 ACK/安全事件缺少保留队列资源

- **状态**：待修复
- **代码证据**：
  - `src/canfd_protocol.c:203-227`：长度 8 的环形队列实际容量为 7，满时只增加丢帧计数。
  - `src/canfd_protocol.c:281-300`、`1057-1080`：ACK 和安全事件的调用方忽略入队失败。
  - 安全状态只上报 RX 丢帧低 8 位，不上报 TX 丢帧。
- **风险**：连续非法命令产生的拒绝 ACK 可以占满紧急队列，导致真正的防撞或故障事件静默丢失。
- **整改要求**：为本地安全事件预留不可被普通 ACK 占用的邮箱；相同安全状态使用最新值覆盖；上报 TX drop 和队列高水位。
- **验收测试**：填满 ACK 队列后触发四路防撞、ESTOP 和 Bus-Off，安全事件必须可观察且延迟满足要求。

### P1-07 RX 队列容量小且缺少协议 ID 白名单

- **状态**：待修复
- **代码证据**：`src/canfd_protocol.c:892-932` 将任意标准 CAN FD+BRS 数据帧先放入仅 7 帧有效容量的软件队列，之后才按 ID 分派。
- **风险**：共享总线未知 ID 突发可以挤掉心跳或 ESTOP；软件队列满和硬件 FIFO overflow 的诊断语义也没有清晰区分。
- **整改要求**：配置硬件接收过滤器或在 ISR 入队前只允许协议控制 ID；ESTOP 使用独立高优先级接收路径；区分非法格式、软件队列满和硬件 overflow 计数。
- **验收测试**：满总线未知 ID 洪泛时测量 ESTOP 延迟、心跳连续性和丢帧诊断。

### P1-08 控制任务内阻塞串口输出影响 10 ms 周期

- **状态**：待修复
- **代码证据**：
  - `src/chassis_motion_controller.c:847-877`、`1173-1177`：控制任务每 100 ms 格式化并输出长遥测。
  - `src/debug_uart_log.c:33-49`：日志可永久等待互斥锁。
  - `at32f45x_board/at32f45x_board.c:90-98`：每个字符轮询等待 USART 发送完成。
- **风险**：115200 波特率下长日志可占用或阻塞超过一个控制周期，增加制动延迟和速度环抖动。
- **整改要求**：控制任务只写固定长度快照；格式化和 UART 发送移至低优先级 StatusTask，并使用有界缓冲和丢弃策略。
- **验收测试**：测量控制循环 WCET、抖动以及日志满载时的防撞到制动延迟。

## 5. P2：协议可维护性与扩展问题

### P2-01 ACK 缺少 session/事务 ID，重试语义不完整

- **状态**：建议在协议 V1.1/V2 处理
- **现象**：ACK 只有 sequence 和 device ID；新 session 可重用序号，而旧 ACK 队列不清理。相同序号重发只返回 DUPLICATE，不重放原 ACCEPTED/COMPLETED 结果。
- **风险**：跨会话旧帧误关联；ACK 丢失后，主机无法通过幂等重试取得原最终结果。
- **建议**：ACK 回显 session 或使用全局 transaction ID；缓存有限数量事务的最终结果并支持重放。

### P2-02 单节点固定 ID，不支持多电机板共享总线

- **状态**：待整车拓扑确认
- **现象**：`CANFD_PROTOCOL_NODE_ID=1`，命令无目标节点，所有同类板使用相同遥测 ID；安全帧不携带 device ID。
- **风险**：多板时命令同时执行、状态帧仲裁冲突且来源不可区分。
- **建议**：若整车总线可能有多板，增加目标节点、源节点和节点配置机制，或采用按节点分配的 CAN ID 区间。

### P2-03 状态序号为所有遥测 ID 共用，语义未写清

- **状态**：待明确
- **现象**：`0x201/0x211/0x221/0x231` 共用一个 `canfd_status_sequence`，单个 ID 的接收序号会自然跳变。
- **风险**：上位机若按每个 ID 独立检测丢帧，会产生误报。
- **建议**：协议明确它是全局事件序号，或改为每个遥测流独立序号。

### P2-04 参数拒绝原因会被错误映射为 UNSUPPORTED

- **状态**：待修复
- **现象**：通用命令校验允许较宽范围，底盘控制器再限制为前进 300..3000 mm、50..100 mm/s；底盘拒绝后，协议层无详细原因，只能映射为 UNSUPPORTED。
- **风险**：主控不能区分参数越界、当前平台不支持和其他拒绝条件。
- **建议**：命令处理结果携带明确 `motion_command_error_t`，保留 RANGE、FAULT_LOCKED、UNSUPPORTED 等原因。

### P2-05 Heartbeat 和未知控制操作的 ACK 命令类型错误

- **状态**：待修复
- **现象**：Heartbeat 公共校验和未知控制操作均以 STOP 类型生成拒绝 ACK。
- **风险**：日志和主控诊断会误认为 STOP 被拒绝。
- **建议**：为 Heartbeat/Control 定义线级命令类型，或让解析错误 ACK 回显原 CAN ID/操作码。

### P2-06 CAN 恢复后可能发送过期普通遥测

- **状态**：待修复
- **现象**：CAN3 恢复时清 RX 和硬件在途状态，但保留普通 TX 队列；链路恢复后可能先发送故障前积压的旧遥测。
- **风险**：上位机短时间看到过期位置、转速或状态。
- **建议**：恢复时清除普通遥测队列，或改为按 ID 保存“最新快照”，恢复后只发送最新状态；安全事件仍需可靠保留。

### P2-07 上位机没有完整区分 USB 写入、gs_usb echo 和板端 ACK

- **状态**：待修复
- **现象**：GUI 在 USB Pipe 完整写入后即增加 TX 成功计数；gs_usb TX echo 和 CAN error frame被忽略；RawControl 不解析 `0x181` 事务状态。
- **风险**：用户无法区分“进入 USB”“适配器处理”“板端接收/接受/完成”，容易把没有执行误判为已发送。
- **建议**：分层显示 USB write、adapter echo/error、板端 RECEIVED/ACCEPTED/COMPLETED，并以板端 ACK 作为动作成功依据。

### P2-08 Qt CAN 原始数据池和日志策略导致稳定卡顿

- **状态**：根因已确认，待修复
- **代码证据**：
  - `CanFramePlugin.cpp:122-129`：每个 payload 字节转为一个数值样本。
  - `RingBufferPool.h:52`：默认全局池 100000 samples。
  - `DebugCore.cpp:119-137`：正常环形覆盖也发出 overflow 事件。
  - `MainWindow.cpp:58-68`、`690-696`：每次 overflow 都追加到无上限文本日志。
- **影响**：按当前遥测周期约 2208 sample/s，约 45 s 后开始逐帧输出 dropped 24/32，与现场截图一致，并持续拖慢 UI。
- **建议**：Raw payload 默认不进入数值池；只解码需要绘图的字段；正常环形覆盖不视为错误；日志限频、合并并设置最大行数。

### P2-09 上位机协议逻辑重复且快捷序号固定

- **状态**：待重构
- **现象**：CRC、ID、session 和字段编码分别复制在 `RawControlPlugin.cpp`、`AgvCanFdTest.cpp` 和 Python 工具中；GUI 的 Clear、Move、Stop 使用固定命令序号。
- **风险**：协议升级容易产生实现漂移；同一 session 第二次 Move 会收到 DUPLICATE。
- **建议**：建立共享 `AgvCanFdCodec` 和 `SessionController`，统一分配 session/sequence、生成心跳并解析 ACK/安全状态。

### P2-10 gs_usb 接收缺少跨 ReadPipe 残帧缓存

- **状态**：待增强
- **现象**：每次 WinUSB ReadPipe 独立解析，尾部不足一个 20/76 字节记录时直接丢弃。
- **风险**：当前适配器通常返回完整记录，现有实测可用；遇到短读、非整数倍合并包或其他兼容固件时可能丢帧。
- **建议**：保留跨读取残余字节，按完整 gs_usb 记录持续解析，并增加分片/粘包测试。

## 6. 其他工程问题

### E-01 PID 仍是台架初值

- 当前参数为 20 ms、左右轮共用 `Kp=4.0`、`Ki=8.0`、`Kd=0`，并带前馈、积分抗饱和和 PWM 斜坡。
- 该结构作为低速台架基线合理，但不是整车带载最终参数。
- 需要分别记录左右轮阶跃响应、稳态误差、PWM、峰值电流、制动距离和不同电池电压下的表现后独立整定。

### E-02 编码器异常尚未纳入正式故障判据

- 非法跳变计数目前只上报；里程进度使用左右绝对计数。
- 线束干扰、单侧断线或毛刺可能产生虚假进度、误判到达或掩盖堵转。
- 应增加单侧无脉冲、方向不符、非法跳变率和左右速度差的故障判据。

### E-03 启动时没有接收节点会锁存历史 CAN 故障

- 底盘从启动即发送周期遥测；无其他节点 ACK 时，50 ms TX 超时会锁存 `0x0020`。
- 这解释了 USB-CAN 连接后通常需要 CLEAR_FAULT 的现场现象。
- 应区分“空闲时无主控在线”和“运动过程中链路丢失”，并明确启动/建链/ARM 状态。

### E-04 活动模式和架构说明已经过期（2026-08-19已关闭）

- 生产入口已经固定为`src/main.c`，`app_mode.h`和历史测试模式已移除；
- `AGENTS.md`已重写为当前FreeRTOS、CAN FD、安全和能力边界；
- 生产Keil工程不再编译独立硬件测试状态机。

### E-05 部分源码注释存在编码乱码（2026-08-19已关闭）

- 多个电机、底盘和上位机源文件的中文注释显示为乱码。
- 不直接改变运行结果，但会降低硬件、安全意图和调试假设的可维护性。
- 第一方`src/*.c/.h`已经统一为UTF-8；厂商库和无关文件未做批量转换。

## 7. 推荐整改顺序

1. 修复 `P0-01`、`P0-02`：安全代际、队列屏障、旧命令作废和 ARM 状态。
2. 修复 `P1-01`、`P1-02`：由控制器维护真实 lease，心跳必须递增且可判新鲜。
3. 修复 `P1-03`：上位机有界发送队列、心跳合并、STOP/ESTOP 抢占和断线代次。
4. 修复 `P1-04`、`P1-05`、`P1-06`、`P1-07`：链路健康状态机和 CAN 资源保证。
5. 增加异常安全门、看门狗、过流/欠压和物理急停，完成 `P0-03`、`P0-04`。
6. 统一协议 codec、ACK 事务语义和节点寻址，处理 P2 问题。
7. 完成架空轮故障注入后，再做四路防撞、带载 PID 和整车落地测试。
